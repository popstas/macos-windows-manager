# Окно настроек и тумблеры фич

Дата: 2026-08-14. Задача из `docs/TODO.md`: «Settings window, feature flags
основных фич, по умолчанию всё включено».

## Что решаем

У трекера сегодня нет ни одного способа что-либо настроить, кроме правки
`~/.config/macos-windows-manager/config.yaml` руками, и нет способа выключить
отдельную фичу вовсе. Расстановка окон — самая заметная человеку фича и первая,
которую хочется отключить, не выключая трекер целиком; сегодня для этого нет
ничего.

Окна у приложения нет вовсе: в `tauri.conf.json` стоит `"windows": []`,
`frontend/index.html` — заглушка в одну строку, `ActivationPolicy::Accessory`
намеренно убирает значок из дока, каталога `src-tauri/capabilities/` нет, и
YAML в проекте никто ни разу не писал — только читал. Всё это заводится с нуля.

## Что берём у соседа

`ccfzf-picker` — то же приложение на Tauri 2, и всё перечисленное там уже
работает. Берём оттуда не код ради экономии, а решения вместе с причинами, за
которые там уже заплачено выкатками:

| Оттуда | Что именно |
|---|---|
| `src-tauri/src/config_file.rs` | слияние патча, отказ на `null`, шапка, `.bak`, `0600` |
| `open_settings` в `main.rs` | ленивое окно, `async`-команда, переиспользование окна |
| `capabilities/default.json` | список окон и `core:default` |
| `settings.html` | самодостаточная страница, `window.__TAURI__.core.invoke` |
| `ActivationPolicy::Accessory` + окно | сочетание проверено там на живом маке |

Форму **не** копируем: у пикера она рисуется из схемы (`config-shape.js` +
`settings-form.js`, копирование в `frontend/` скриптом `prepare-frontend.js`) —
там под полсотни полей на пяти вкладках. У нас четырнадцать, а npm в проекте
нет вовсе. Заводить `package.json`, каталог `frontend-src/` и шаг сборки ради
одной страницы — плата без покупки. Если форма когда-нибудь дорастёт до
пикерских масштабов, эта машинерия заводится отдельной задачей, и ничего из
сделанного здесь не пропадёт.

## 1. Флаги: где живут и как их видит трекер

Три тумблера, все включены по умолчанию:

```yaml
features:
  placement: true   # расстановка окон
  snapshots: true   # снимки раскладки
  requests: true    # просьбы по MQTT
```

Разбор — в `parse_config`, по тому же правилу, что у остальных полей:
`unwrap_or(true)` **на каждый флаг отдельно**, чтобы мусор в одном не стоил двух
других, а `features:` не-словарём не стоил всех трёх. Отсутствующий блок — все
включены: конфиги, которые уже лежат на маках, обязаны вести себя ровно как
сегодня.

Публикация файла окон (`deliver::send`) и поход за индексом сессий по ssh
(`dump::Cache`) тумблеров **не получают**. Без первой пикер эту машину не видит
вовсе, без второго заголовки не привязываются к сессиям и файл окон едет пустым
по смыслу — это не «фича», а сам трекер, и выключатель для него называется
`Quit`.

### Применение на лету

`run_tracker` читает конфиг **один раз**, в самом начале. Без починки этого
сохранённый тумблер молчал бы до перезапуска, а молча не подействовавший
тумблер хуже отсутствующего.

Починка — разделяемая ячейка по образцу `Trusted`: `Arc<Mutex<Config>>`,
которую такт трекера читает в начале оборота, а команда сохранения обновляет
после успешной записи файла. Копия конфига на такт — плата пренебрежимая:
такт секундный, структура мелкая.

На лету подхватываются флаги, `terminals`, `tickMs`, `sshHost`, `remoteDir`,
`windowHost` — всё, что читается по месту каждый оборот. Поля `mqtt:` и блок
`state:` — нет, и форма говорит об этом прямо (см. раздел 4): поток подписки
поднят на старте и останавливаться не умеет, а пути состояния держат уже
загруженные слоты. Учить поток подписки останавливаться — не эта задача.

### Три гейта в такте

- **`placement`** — пропускается цикл `for (window_id, want) in
  tracker.placements()`. Слоты продолжают вестись и `state.json` продолжает
  писаться; выключается только `ax::place`. Иначе выключенный тумблер стирал бы
  человеку запомненные места окон — а вернув тумблер обратно, он не вернул бы
  их.
- **`snapshots`** — пропускается ветка `decide`/`append`/`update_last` вместе с
  записью `snapshots.json`.
- **`requests`** — просьбы из канала вычитываются (иначе очередь копилась бы), но
  не исполняются, **и `focus` в файле окон объявляется как `link.is_live() &&
  features.requests`**. Второе — не косметика: объявить умение поднимать окно,
  не собираясь его поднимать, значит подарить человеку молчащий Enter в пикере,
  а это, как записано в README, хуже открытого терминала. Поток подписки при
  этом не трогается.

## 2. Окно, трей и жизнь процесса

### Крестик не должен гасить трекер

Проверено по исходникам, а не по памяти —
`tauri-runtime-wry-2.10.0/src/lib.rs:4177`:

```rust
TaoWindowEvent::Destroyed => {
  let removed = windows.0.borrow_mut().remove(&window_id).is_some();
  if removed {
    let is_empty = windows.0.borrow().is_empty();
    if is_empty {
      callback(RunEvent::ExitRequested { code: None, tx });
      ...
      if !should_prevent { *control_flow = ControlFlow::Exit; }
```

Сегодня это не стреляет только потому, что окон нет вовсе и `Destroyed` не
приходит никогда. С первым же окном крестик на форме гасил бы трекер: значок
пропал из строки меню, публикация встала, а человек всего лишь закрыл
настройки.

`main()` перестаёт быть `.run(generate_context!())` и становится `.build(…)` +
`.run(|_app, event| …)` с одной веткой:

```rust
tauri::RunEvent::ExitRequested { code: None, api, .. } => api.prevent_exit(),
```

Именно `code: None`. `app.exit(0)` из пункта `Quit` приходит тем же событием, но
с `code: Some(0)` (`Message::RequestExit`, там же, строка 4217) — глухой
`prevent_exit()` сделал бы трей неубиваемым.

### Меню и команда

Пункт `Settings…` встаёт над `Quit`: `[status] [grant, пока нет разрешения]
[Settings…] [Quit] [version]`. `GRANT_POSITION = 1` остаётся верным — приходящий
и уходящий пункт по-прежнему второй сверху.

```rust
#[tauri::command]
async fn open_settings(app: tauri::AppHandle) -> Result<(), String>
```

`async` здесь не украшение и не задел: синхронную команду Tauri исполняет прямо
в потоке цикла событий, а создание webview этот же цикл и ждёт — окно
появляется, страница в нём не грузится никогда, остаётся белый прямоугольник.
Заплачено этим пикером; повторять круг незачем.

Окно создаётся лениво и переиспользуется: повторный вызов делает `unminimize` +
`show` + `set_focus`. В `"windows": []` оно не объявляется — объявленное
поднималось бы на старте, и второй webview висел бы в памяти у каждого, кто в
настройки не заходит.

### Конфигурация сборки

- `"withGlobalTauri": true` — даёт `window.__TAURI__.core.invoke` без бандлера.
- `src-tauri/capabilities/default.json` — окна и `core:default`.
- `frontend/settings.html` ложится рядом с заглушечным `index.html`;
  `frontendDist: ../frontend` копирует каталог как есть, шага сборки нет.

## 3. Запись конфига

Новый `src-tauri/src/config_file.rs` — порт пикерского, вместе с зависимостью
`serde_yaml` (сейчас она только у `mwm-core`). Правила и причины:

- **Патч, а не файл целиком.** Форма знает не про все ключи (блок `state:` в неё
  не входит), перезапись стёрла бы остальное молча.
- **Вложенные словари сливаются по ключам.** Иначе `mqtt.password`, который
  форма не показывает и обратно не шлёт, стирался бы на каждом сохранении.
- **`null` отклоняется на любой глубине.** Не только `{"mqtt": null}`, но и
  `{"mqtt": {"password": null}}` — второй стирает ровно тот ключ, ради которого
  написано слияние по ключам.
- **`.bak` кладётся один раз, перед первой перезаписью.** Комментарии после неё
  не восстановить ничем, а бэкап на каждое сохранение затирал бы оригинал его же
  вчерашним состоянием. Файл из одних пробелов бэкапу не подлежит — иначе он
  занял бы единственный слот навсегда.
- **`0600` на файл и на бэкап, до переименования, а не после.** Иначе есть
  промежуток, в котором пароль уже на месте, а права ещё общие.
- **Шапка-предупреждение** о том, что файл переписывается целиком и комментарии
  не сохраняются, со ссылкой на `config.yaml.bak` и на `config.example.yml` как
  на документацию ключей. Шапка — комментарий, разбор её выбрасывает, на втором
  сохранении она не удваивается.

Файловая часть (`write_config`) отделена от команды: чистая операция без
`AppHandle`, её накрывают тестами во временном каталоге, не поднимая Tauri.

## 4. Форма

Четыре группы, четырнадцать полей:

| Группа | Поля | Когда действует |
|---|---|---|
| Features | `placement`, `snapshots`, `requests` | со следующего такта |
| Connection | `sshHost`, `remoteDir`, `windowHost` | со следующего такта |
| Windows | `terminals` (список строк), `tickMs`, `dumpCacheMs` | со следующего такта |
| MQTT | `host`, `port`, `user`, `password`, `base` | **после перезапуска** |

Пометка «takes effect after restart» стоит на всей группе MQTT — по причине из
раздела 1.

Блок `state:` в форму не входит: пути, `keep` и `debounceMs` правят раз в жизни,
а слияние патча сохранит их нетронутыми и без редактора.

### Две картины конфига вместо одной

У пикера `load_config` отдаёт сырой YAML, и умолчания живут второй копией в
JS-схеме. У нас умолчания — это `parse_config`, и вторая их копия в
`settings.html` разошлась бы с первой на первой же правке. Поэтому команда
отдаёт обе картины:

```json
{ "file":      { "…": "что лежит в config.yaml" },
  "effective": { "…": "что подхватил трекер, с умолчаниями" } }
```

В поля подставляется `file`; `effective` показывается подсказкой рядом («не
задано — действует 1000»). Патч собирается **только из тронутых полей**,
сравнением с `file`: человек, ничего не менявший, получает файл без изменений, и
умолчания в него не впечатываются.

Побочная польза, ради которой это стоит отдельного упоминания: окно честно
отвечает на вопрос «а какой конфиг сейчас в работе» — тот самый вопрос, с
которого начинается расследование молчащего трекера.

Пароль: поле пустое, уходит в патч только если в него что-то ввели.

Сохранение: `save_config` пишет файл, перечитывает его, кладёт свежий `Config` в
общую ячейку и возвращает статус; форма перечитывает обе картины и показывает
результат.

## 5. Проверка

### Тесты (Linux, обычный `cargo test --workspace`)

`src-tauri` собирается на машине разработки целиком — macOS-ветки под `cfg`, —
поэтому тесты `config_file` гоняются здесь же.

- `config_file`: чужой ключ переживает запись; `mqtt.password` переживает правку
  соседнего поля; список заменяется целиком; `null` отклоняется на верхнем
  уровне и во вложенном; шапка не удваивается; `.bak` кладётся один раз и вторым
  сохранением не затирается; файл из пробелов бэкапу не подлежит; права на файле
  и бэкапе `0600`; отказавшийся патч не трогает файл; отсутствующий каталог
  создаётся.
- `parse_config`: блока `features:` нет → все три включены; поле читается; мусор
  в одном флаге не стоит двух других; `features:` не-словарём → все включены.

### Два теста-сторожа текстом по исходнику

Приём уже применён в пикере (`tray_opens_settings_off_the_event_loop` читает
`main.rs` и сторожит форму вызова). Здесь он закрывает то, что руками ловится
только глазами и только на живом маке:

- ветка выхода сторожится на `code: None` — глухой `prevent_exit()` сломал бы
  `Quit`, а заметить это можно, только попробовав выйти;
- `focus` в файле окон сторожится как `is_live() && requests` — разъехаться эти
  двое могут молча, а цена — молчащий Enter у человека в пикере.

### Руками на маке (чеклист в PR)

- пункт `Settings…` открывает окно, и окно выходит вперёд;
- значка в доке нет, пока окно открыто;
- **крестик на окне не гасит трекер**, а `Quit` по-прежнему гасит;
- сохранение кладёт `.bak` один раз и ставит `0600` на файл и бэкап;
- выключенная расстановка перестаёт двигать окна, но `state.json` продолжает
  вестись, и включённая обратно расставляет окна, появившиеся после включения
  (список расстановок живёт один такт и собирается внутри `tick`, так что
  окно, открытое при выключенном тумблере, останется там, где его положила
  система);
- выключенные просьбы убирают `focus` из опубликованного файла окон, и пикер
  перестаёт предлагать Enter;
- выключенные снимки перестают писать `snapshots.json`;
- правка полей MQTT действует после перезапуска, остальное — со следующего такта.

## Что не входит

- Тумблеры для публикации файла окон и для ssh-индекса сессий (причина в
  разделе 1).
- Редактор блока `state:`.
- Остановка и перезапуск потока подписки MQTT на лету.
- Схема полей, генератор формы, `package.json`, шаг сборки фронтенда.
- Хоткей на открытие настроек: у трекера нет ни одного глобального хоткея, и
  заводить первый ради формы, которую открывают раз в месяц, незачем.

## Открытые вопросы — проверяются только выкаткой

Помечены как открытые намеренно: код под `#[cfg(target_os = "macos")]` на машине
разработки не компилируется вовсе, и ответы на них видны только на маке.

1. Выйдет ли окно вперёд у `Accessory`-приложения по клику из меню трея.
   Сочетание проверено в пикере (`main.rs:1090` — тот же `Accessory`, и
   настройки там открываются), но пикер перед созданием окна гасит своё, а нам
   гасить нечего — путь чуть другой. Если не выйдет: `set_focus()`, а если мало
   — явная активация приложения через AppKit, тем же приёмом, что уже лежит в
   `ax.rs` для чужих окон.
2. Не появится ли значок в доке, пока окно открыто. `Accessory` обещает, что
   нет, но у приложения до сих пор не было ни одного окна, чтобы это увидеть.
3. Как выглядит `frontendDist` с двумя файлами: `settings.html` станет вторым
   рядом с заглушечным `index.html`.

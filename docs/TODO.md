# next

- [ ] Settings window: окно настроек с тумблерами основных фич, по умолчанию все включены. Выключаемое (по местам в коде): расстановка окон (`tracker.placements()` + `ax::place` в `run_tracker`), снимки раскладки (`mwm_core::snapshots`, запись `snapshots.json`), просьбы по MQTT (`mqtt::spawn` и `serve` — подъём окна и пометка непрочитанным), поход за индексом сессий по ssh (`dump::Cache`), публикация файла окон (`deliver::send`). Что выяснилось при разведке и стоит решить до реализации:
  - Окна у приложения нет вовсе: в `tauri.conf.json` `"windows": []`, `frontend/index.html` — заглушка в одну строку, а `ActivationPolicy::Accessory` в `setup` намеренно убирает значок из дока. Settings станет первым окном, и Accessory-приложение своё окно вперёд само не выводит — нужна явная активация, иначе пункт меню будет выглядеть не сработавшим. Каталога `src-tauri/capabilities/` нет — под окно и команды придётся заводить ACL
  - Флагам место в `parse_config` (блок `features:`), с тем же правилом, что у остальных полей: своё умолчание на поле, а не отказ на весь блок, — то есть `unwrap_or(true)` покомандно
  - Конфиг читается один раз, в начале `run_tracker`, и перечитывания нет. Либо флаги живут в разделяемом состоянии и спрашиваются каждый такт (как `Trusted`), либо смена требует перезапуска — и тогда об этом обязано быть сказано в самом окне, молчаливо не подействовавший тумблер хуже отсутствующего
  - Записи YAML в проекте нет вовсе, конфиг только читается. Перезапись файла целиком снесёт комментарии, которые человек писал руками, — либо править точечно, либо хранить флаги отдельным файлом состояния рядом со `state.json`
